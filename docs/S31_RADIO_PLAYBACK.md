# S31 网络收音机连续播放

## 2026-10-29：保护解码和 PCM 输出任务

BH1098G 提供 16 kHz I2S 时钟，DMA 为 6 个描述符、每个 240 个采样帧，容量约 90 ms。网络播放器的同一条任务流水线执行解码、重采样及同步 I2S 写入。此前这条任务优先级为 5，而 `RadioActivity` 把 CPU0 上的 UI 主任务提升到 10；较长的 UI 绘制可能导致 PCM 输出任务得不到运行，耗尽 DMA 音频。

S31 网络播放器优先级改为 12，保持 CPU0、原有栈和缓冲大小。HTTP 任务为 10、HLS 提取任务为 9、收音机 UI 主任务为 10。音频任务在 I2S 写满后阻塞，给 UI 和输入任务运行机会；Wi-Fi 系统任务仍高于音频任务。此改动不调整本地音乐及 P4 输出路径。

增加 `radio PCM supply gap` 日志：统计前一次输出回调完成至下一次回调开始的间隔，排除正常阻塞写入 I2S 的时间。间隔达到 DMA 理论容量的三分之二时计数，首次及后续最多每 5 秒打印，包含间隔、DMA 容量、次数和实际任务优先级。首次播放、暂停及状态切换重置间隔基准。该日志说明供流延迟，不能单独证明硬件已经欠载；DMA 实际余量可能小于理论容量。

用户日志的 `No more data, rlen=0, errno=0` 位于 HLS TS 分段尾部，是正常文件读完。TS 每段约 10 秒、约 253 KB；换段/更新播放列表需要重新打开 HTTP，但这段日志没有足够信息证明卡顿必然由网络、界面或解码中的某一处造成。128 KB HLS 缓冲原本就在输入任务中运行，不应把整个 TS 的读取历时直接当成纯下载耗时。

设备验证：连续播放 HLS 和 MP3 电台，覆盖每分钟状态栏刷新、打开/关闭控制中心及切台。若仍出现卡顿，保留卡顿前后的 `radio PCM supply gap`、HTTP/HLS 与界面刷新日志，继续定位供流延迟来源。编译通过不能代替实际连续播放验证。

## 电源键待机时的网络与功放退出顺序

收到电源键短按后，原流程直接关闭 Wi-Fi、销毁 netif，而收音机 HTTP/HLS 输入任务尚在运行。用户崩溃栈为 `esp_http_client_read -> lwip_recv -> pbuf_free -> esp_netif_free_rx_buffer`，此时 netif 的接收释放回调已失效，导致 Instruction access fault；崩溃也使功放来不及静音。

活动新增 `prepare_standby()` 可失败准备阶段，S31 在待机和关机共同流程里、网络关闭前调用。收音机先关闭 PA，再完整停止并销毁播放器及 HTTP/HLS 输入任务，随后释放 I2S/BT。暂停播放器不足以满足此要求，因为输入任务可能仍在预读。停止返回错误时否决本次电源操作，保留网络接口。

正常待机保留当前电台选择，醒来后保持停止状态，由用户点击播放恢复；后台播放任务先连接 Wi-Fi，再启动网络音频，覆盖按需 Wi-Fi 模式。播放启动或切台任务尚未返回时，沿用 `can_standby()` 延后电源操作。软件关机也经过相同的准备阶段。`tools/test_radio_standby.py` 使用生产方法及待机前置代码，验证静音/回收/关闭网络的顺序、失败取消、启动期间延后及唤醒重连；仍需设备验证 HLS、MP3、暂停、播放和切台期间的短按/长按。

## 域名解析失败与重复诊断查询

2026-10-30 日志中 `getaddrinfo()=202` 对应 SDK 的 `EAI_FAIL`，当次诊断查询约13秒；HTTP随后再解析同一域名并失败，合计约27秒。移除 `HTTP_STREAM_PRE_REQUEST` 中用于日志的同步 `getaddrinfo()`，由HTTP连接自身执行解析，避免诊断额外发送查询和重复等待。日志里的播放请求返回成功只表示异步启动已提交，不能证明DNS/HTTP已成功，相关日志改为 `Playback start submitted`。

电脑处于同一局域网（192.168.0.100），针对 `ngcdn002.cnr.cn` 的单次UDP查询测试中，DHCP提供的192.168.1.1和192.168.0.1均正常返回，公共DNS223.5.5.5也正常返回；不能据此把设备侧DNS失败归因为DHCP地址配置错误，也不能用PC结果证明设备接收链路正常。

S31收音机开始连接前，仅在默认路由确为Wi-Fi、第三个 `ESP_NETIF_DNS_FALLBACK` 槽位为空时填入223.5.5.5；保留原有主备DNS及已配置的非空fallback。lwIP在前序DNS失败后使用fallback，仍可能产生DNS重试等待；不硬编码电台/CDN地址，不替换URL、Host或SNI。切台时已联网则直接复用连接，离线/待机唤醒才执行联网初始化。设备侧为何没收到解析响应仍需实际复测确认。

## 多秒 PCM gap 的分级观察与 HTTP 缓冲

用户后续日志出现1929／5687／3576ms的PCM供流间隔，远超约90ms的DMA容量；多个间隔发生时没有EPD刷新。约10秒、253800字节的TS分段，从打开到HTTP读完历经约32秒，但该历时包含消费反压，不能直接当成纯下载耗时或据此断言是哪级网络故障。

S31 HTTP原始压缩数据环形缓冲由20KiB增至128KiB，HLS输出缓冲保持128KiB，额外108KiB通过GMF的PSRAM分配器分配。没有新增PCM缓存或人为预缓冲等待，实际能抵挡的抖动仍取决于队列已填充数据及平均下载速度，持续带宽不足无法靠扩大缓存解决。

`radio PCM supply gap` 每5秒最多一条（首次间隔直接记录），先把恢复的PCM写入I2S，再打印统计，避免打印延长已经发生的断供。新增字段：

- `window`：自上一条gap日志以来的近似统计窗口；`http_bytes`为该窗口从HTTP原始缓冲消费的字节。
- `http_wait_max`：等待HTTP原始缓冲的最大耗时，包含上游取流与HTTP任务供流等待，不等价于单个TCP读取耗时。
- `input_bytes`、`input_wait_max`：解码器从HLS输入缓冲获取数据的字节数和最大等待；直接MP3没有独立HLS层，这组计数保持0。
- `http_buf_before`、`input_buf_before`：各层最近一次读取前的队列填充量，属于采样值，不是gap发生瞬间的同步快照。

HTTP侧沿用SDK默认数据总线读取／释放语义，HLS侧委托原始filter处理metadata、格式切换及有效载荷。安装后的HTTP对象工厂保留到pool副本，覆盖HLS内部创建的HTTP对象，不修改managed component。`tools/test_s31_radio_flow.py` 覆盖有效块所有权、EOF／abort／timeout、HLS委托及HTTP副本配置。设备复测时对照长gap、各层等待和缓冲采样继续定位，不把本轮修改视为已证实消除所有卡顿。
# S31 收音机启动时的 PCM 栈保护故障

2026-10-31 的实机记录显示：播放列表、TS 分片读取成功，解码输出 `16000 Hz 2 ch 16 bit`，播放器进入 RUNNING 后，在 `write_pcm` 触发 Stack protection fault。GMF 任务栈约 8 KiB，故障 SP 已低于栈下界。

反汇编确认 Debug 构建为 `write_pcm` 两个分支中的 4 KiB 局部数组同时预留空间，函数自身栈帧达到 **8224 字节**，尚未计算 GMF 回调及转换器调用。问题与此时能否联网、是否接着耳机无关，外放分支也会触发。

已改为一次申请、重复使用的 **4096 字节 PSRAM 工作区**，USB packed PCM 与 BH1098G 展开输出复用该块内存。完整 PCM 转换及提交均由 `s_pcm_mutex` 串行保护；停止并加入音频任务后，在反初始化时释放。申请失败明确返回失败，不逐块申请，也不占用新的 SRAM 缓冲。调整后本函数栈帧为 **48 字节**（不含下层调用），GMF 栈配置保持原值。首次使用时日志记录任务的最小剩余栈，供实机确认余量。

`tools/test_s31_pcm_workspace.py` 提取生产写出函数，验证跨 512 帧边界的 native24 输出、外放槽布局、同一工作区复用、拔出暂停和申请失败处理。完整 S31 构建通过；需要实机重新验证收音机播放及 USB 输出。

## 同期 USB 启动恢复

收音机等待 HTTP/HLS、尚未收到第一块 PCM 时，S31 也继续执行 USB 枚举与重试，避免瞬态 VBUS 状态使 AUTO 长时间留在外放。网络管线的 16-bit PCM 日志现在标明实际末端是 USB 转换还是 BH1098G。供电拒绝日志包括 STATUS1、VBUS_type、CTRL1、CTRL3、EN_OTG；仅在明确报告 OTG 状态且开关已开启时接管主控重启遗留状态，外部供电仍拒绝。先前那份简短记录在 HOME 退出后才报告连接中止，不能仅据此判定网络自身故障。

## MP3 电台播放中的 CPU0 看门狗与重采样预算

2026-10-31 后续日志中，蜻蜓 MP3 电台已成功连接、解码并持续输出；PCM 工作区建立后最小剩余栈为 6244 字节，没有重现先前的栈保护故障。随后反复报告 IDLE0 看门狗，CPU0 正在执行 ASP 音频任务，多次地址解码指向 `fa_resample_process`。PCM 供流间隔反复达到 137～139 ms，超过 BH1098G 约 90 ms 的 DMA 容量；后续 HTTP 缓冲读取最大等待只有约 4 ms。该记录支持优先排查重采样和调度，不能把所有 gap 都归因于网络。记录后半段同一地址被标成 HLS 函数，说明符号解码并不始终匹配，不能据此断言 MP3 正在运行 HLS 过滤器。

仅 S31 收音机在管线启动前包装其重采样元素，使用 SDK 的 complexity=1、SPEED 配置，保留滤波重采样和固定硬件目标采样率；本地音乐及 P4 配置不变。较低复杂度会改变滤波质量，需要实机试听。SDK 内部格式重开继续保留此配置。包装保留原操作返回值，每 5 秒在 PCM 写入后汇总转换元素的平均/最大耗时及实际源/目标采样率；元素耗时包含端口等待，并非纯算法 CPU 时间。

此前假定 I2S 写满后必然阻塞，但当生产慢于消费时，写入可能持续立即返回，高优先级任务因此长时间不给 IDLE0 运行机会。现在 PCM 提交后、释放 `s_pcm_mutex` 后，每至少 250 ms 主动阻塞 1 tick（当前 100 Hz，约一个 10 ms tick），给较低优先级任务运行机会。该主动等待不计入下一次供流 gap。没有关闭、延长或反复喂看门狗，也没有增加整块 PCM 队列。低优先级任务的实际运行仍取决于同核其他任务负载。

`tools/test_s31_radio_schedule.py` 验证生产包装的配置、返回值/格式传播、限频让出、计时归零及时间回绕。仍需实机长播该 MP3 电台、央广 HLS 以及 USB 输出，检查看门狗、gap 和试听效果；若转换仍超过实时预算，继续根据新增统计定位，不将编译成功视为性能验证完成。

## 区分 HTTP 生产端读取与缓冲消费等待

后续 44.1 kHz 日志中重采样平均约 1.26 ms，48 kHz 日志中约 0.92 ms；没有再次出现此前连续 137～139 ms 的计算阶段断供。新的 817/7861 ms、4820/2505 ms gap，分别对应 812/7856 ms、4816/2500 ms 的 HTTP 缓冲获取等待，读取前缓冲为空。可以判断主要在等输入数据，但尚不能单凭此处的等待判定电台服务器、无线链路或接收任务调度中的哪一项异常。

在 S31 HTTP 对象及其 pool 副本中包装 SDK 原始 `acquire_read`，原样委托，保留 gzip、重连、EOF、abort、原有效载荷及 `release_read` 的所有权规则。计时从生产任务拿到可写缓冲后才开始，排除缓冲已满时等空位的正常反压。此计时覆盖 SDK HTTP 读入、必要的重连/解压及被抢占时间，并不是纯 TCP 或网络往返耗时。

每次限频输出 `radio PCM supply gap` 后，增加同一近似窗口的 `radio HTTP producer`：

- `read_bytes`、`reads`：完成读取得到的字节数、完成的源读取回调数，包含 EOF/错误回调。
- `read_max`：已完成的源读取回调最大墙钟耗时；与 `http_wait_max` 同时升高，支持读取/连接阶段停顿的方向。
- `errors`：SDK 源读取返回负值的次数；内部重连已恢复的错误未必以负值返回。
- `active`：当前尚未返回的源读取回调数；`since_done` 为距最近任一 HTTP 源读取完成的时间，尚未完成过读取时为 0。

HLS 的多个 HTTP 对象合并统计；各原子计数分别采样，不能视为严格同步的单次请求快照。若源读取本身都很短，但消费等待很长，则继续检查打开/换段、缓冲提交及调度，不能直接断言无线故障。本次仅补统计，仍用 128 KiB 压缩数据缓冲，尚未引入播放预缓冲或断供蓄水策略。

## 直接 MP3 电台的限时蓄水

后续生产端日志记录单次源读取最长 5656 ms、另一窗口 2682 ms，均最终成功且错误计数为 0；同期转换仍约 0.9 ms。首次长读取仅造成约 227 ms 的 PCM gap，说明原有环形缓冲已抵消一部分停顿，但不足以覆盖全部波动。生产端墙钟时间仍包含 SDK 内部读取、重连/解压和任务被抢占，不能据此断定服务器或无线中的哪一个有问题。

S31 对当前管线直接使用 `io_http` 的无长度直播流，首次消费前等待现有压缩数据环形缓冲积累 32 KiB，最多 5 秒；实际消费遇到空缓冲后，重新积累 16 KiB，最多 2.5 秒。64 kbit/s 电台对应约 4 秒初始储备、2 秒再缓冲储备，其他码率按字节量变化。阈值不超过实际缓冲容量的一半。超时后按 SDK 原读逻辑继续，仍可能等不到网络数据；不保证抵抗持续带宽不足或任意长停顿，也不保证完全无 gap。代价是增加数秒起播/恢复等待，并逐步落后于直播。

不新增 PCM/压缩数据缓冲，继续使用现有 128 KiB PSRAM 环形缓冲。消费任务每 20 ms 检查取消；切台、退出、待机禁写或 IO abort 时立即退出蓄水等待。正常已有数据时不加等待。有限长度响应绕过蓄水，HLS 播放列表及分片仍沿用原过滤器，不套直播阈值。`radio buffer` 日志明确区分 startup/rebuffer、排队量、目标量、等待和是否达到阈值；蓄水等待不属于 `http_wait_max` 的源缓冲获取计时。

另有一次直接 MP3 在首个输出缓冲扩容后即返回解码 -1，此前尚未进入 PCM 输出，不能与播放中缓冲耗尽混为一谈。该返回码是通用失败，不证明真实根因；之后约 1 秒才出现的 socket-not-connected 也可能是管线错误清理的后果。每次直接 HTTP 首次读入现在打印最多 16 字节十六进制前缀，不改变或消耗数据，用于确认服务端是否返回错误页、ID3/帧头或流中间数据。没有盲目吞掉解码错误或无限重试，仍需失败时的前缀及完整前后日志判断。

`tools/test_s31_radio_buffer.py` 提取生产等待逻辑，覆盖初始及再次蓄水、正常路径、两种超时、有限响应/EOF、20 ms 取消和容量限制；原流测试覆盖前缀观察不消耗载荷。实机需验证直接 MP3 连续播放、切台/退出响应及 HLS 行为。
